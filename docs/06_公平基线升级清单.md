# 从开工样例到可用于IEEE Access正式E2的公平基线：差距清单

**开工样例仅是最小运行骨架。** GitHub Actions+3个容器+来源证明跑通后，不能立即声称“成熟CI/CD基线已充分配置”。正式E2前需团队补齐以下内容，并保存版本/有效权限/实测日志。

| 必须完善的功能 | 当前样例做到了什么 | 正式实验需补什么 | 验收证据 |
|---|---|---|---|
| PR Gate | 由pull_request自动触发unittest | GitHub rulesets或等效强制Required Checks、禁止绕过记录 | 实际策略导出/截图＋被阻断的PR |
| 静态质量与安全扫描 | unittest＋HTTP stage gates；没有SAST等 | 选择并启用真实SAST/依赖扫描器（可考虑CodeQL或其他成熟工具），锁定策略，正常与故障实测 | 扫描器版本、规则、PASS/FAIL run、扫描报告 |
| 固定构件一致性 | 固定Python .pyz，3容器复用同本地Docker image config ID | 保存构建产物SHA256、签发对象digest、三阶段精确构件ID；部署阶段不可重建 | 各阶段SHA或镜像ID记录 |
| Dev/QA/Staging | 同一host上三个独立Docker容器，真实HTTP smoke | 完善测试等级、权限、时序和批准规则；不要冒充生产独立环境 | 三阶段成功/失败原始日志和策略 |
| 真实Attestation | B1使用actions/attest生成签名证明且gh验证 | 明确实际启用的验证语义、身份策略和未覆盖的属性 | 证明bundle / CLI JSON /篡改验证 |
| 发布策略与豁免 | 教学仅以所有健康检查PASS为门禁 | 增加可追溯政策版本、批准者和允许豁免的具体规则；不能有意弱化B0/B1 | 门禁配置、豁免事件、policy hash |
| A1信号全集 | 仅采集三个HTTP探测事件 | 真实CI运行信号边界、独立源系统inventory、collector覆盖证明及全部处置历史 | 独立raw inventory、源抽取规则、覆盖证明 |
| A2后继义务 | 教学单条模拟Finding JSON | 新版A2真正实现并跨至少两个release episode执行，冻结旧历史快照 | 真实执行的时序日志、snapshot hash、后继审计结果 |
| 失败场景公平性 | 教学有A101/A201等有限场景 | 冻结Oracle及故障注入点，B0/B1/B2同commit与初始化状态重复执行 | run_ledger、配置SHA、Oracle冻结哈希 |
| 集成开销 | 仅有本地wall-clock训练耗时 | E3记录B1→B2新增工时、适配代码、CPU/RSS、各阶段耗时和端到端性能 | git diff、工时表、原始CSV、脚本再生图表 |

**提醒**：基线本身若已被正确配置并能检出某类故障，必须诚实记为B0/B1已检出；工具不可用是N/A；B2获得新增字段必须把采集成本计入。不得仅因教学样例B0显示PASS就得出现代CI/CD普遍漏检的论文结论。
